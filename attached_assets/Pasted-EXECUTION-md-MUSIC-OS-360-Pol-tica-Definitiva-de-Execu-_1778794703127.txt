EXECUTION.md — MUSIC OS 360
Política Definitiva de Execução Controlada, Preservação Estrutural e Anti-Overengineering
OBJETIVO DESTE DOCUMENTO

Este documento define:

limites absolutos de execução;
regras obrigatórias de alteração;
políticas anti-destruição;
políticas anti-overengineering;
ordem de prioridade real;
regras de preservação estrutural;
regras de segurança operacional;
regras de modificação incremental.

Este documento NÃO define arquitetura.

Este documento NÃO define stack.

Este documento NÃO define governança.

Essas definições pertencem exclusivamente ao:

GOVERNANCE.md
MAPEAMENTO_ESTRUTURAL.md

Este documento define APENAS:

COMO executar;
O QUE pode alterar;
O QUE NÃO pode alterar;
LIMITES da autonomia do agente.
REGRA ABSOLUTA PRINCIPAL

O agente NÃO possui autonomia arquitetural.

O agente NÃO deve:

reinterpretar o produto;
reinventar a arquitetura;
“modernizar” arbitrariamente;
refatorar por preferência pessoal;
reorganizar por opinião;
aplicar “best practices” genéricas sem necessidade real.

O agente deve operar exclusivamente:

dentro da arquitetura existente;
dentro do stack existente;
dentro da estrutura existente;
dentro das regras do GOVERNANCE.md.
PRINCÍPIO DE EXECUÇÃO

Toda alteração deve seguir:

MENOR IMPACTO POSSÍVEL

Sempre preferir:

correção localizada;
correção incremental;
preservação estrutural;
preservação visual;
preservação operacional;
preservação de contratos;
preservação de APIs;
preservação de UX;
preservação de comportamento.
PROIBIÇÃO ABSOLUTA — ALTERAÇÕES NÃO SOLICITADAS

O agente NUNCA deve executar alterações fora do escopo explicitamente solicitado.

Mesmo que considere a alteração:

“melhor”;
“mais limpa”;
“mais moderna”;
“mais escalável”;
“mais enterprise”.

PROIBIDO:

mover arquivos entre módulos sem necessidade crítica comprovada;

renomear módulos;

alterar estrutura do monorepo.

alterar rotas existentes;

alterar UX consolidada;
alterar comportamento visual;

COMPONENTES

PROIBIDO:

recriar componentes existentes;

PROIBIDO:

adicionar integrações fora do escopo.
POLÍTICA ANTI-OVERENGINEERING
ABSOLUTAMENTE PROIBIDO

O agente NÃO deve criar:

arquitetura hexagonal completa;
microserviços;
event sourcing;
CQRS complexo;
service factories genéricas;
repository pattern sem necessidade real;
wrappers redundantes;
hooks globais artificiais;
providers redundantes;
abstrações sem reutilização comprovada;
“core engines” genéricas;
plugin systems;
dynamic module loaders;
arquitetura “enterprise fake”;
boilerplate desnecessário;
pipelines artificiais;
“universal SDKs” internos;
sistemas genéricos prematuros.
REGRA DE REUTILIZAÇÃO OBRIGATÓRIA

Antes de criar QUALQUER:

componente;
hook;
utilitário;
provider;
service;
helper;
mapper;
schema;
modal;
tabela;
card;
formulário;
abstraction;

o agente DEVE verificar se já existe solução reutilizável no projeto.

Se existir solução equivalente:

reutilizar;
extender minimamente;
preservar compatibilidade.
REGRA DE EVIDÊNCIA OBRIGATÓRIA

PROIBIDO alterar qualquer estrutura sem evidência objetiva de:

bug real;
falha real;
vulnerabilidade real;
duplicação comprovada;
gargalo comprovado;
inconsistência verificável;
risco operacional real.

“Melhor prática” isolada NÃO é justificativa.

“Arquitetura mais limpa” NÃO é justificativa.

“Mais enterprise” NÃO é justificativa.

POLÍTICA DE “NÃO REESCREVER”

reescrever módulos completos;

recriar forms;
recriar layouts;

quando o problema puder ser resolvido localmente.

POLÍTICA DE “NÃO INVENTAR DOMÍNIO”

O agente NÃO pode:

criar novos domínios;
criar novos módulos;
criar novos conceitos de negócio;
reinterpretar regras operacionais;
redefinir escopo do produto.
POLÍTICA DE EXECUÇÃO FINAL

O agente deve atuar como:

executor controlado;
mantenedor arquitetural;
estabilizador incremental.

NÃO como:

redefinidor do sistema;
reestruturador agressivo;
arquiteto autônomo;
“reinventador” da plataforma.

O resultado esperado é:

maior estabilidade;
menor débito técnico;
melhor segurança;
melhor isolamento multi-tenant;
melhor observabilidade;
melhor performance;
melhor consistência;

SEM:

destruir arquitetura;
reinventar estrutura;
quebrar UX;
quebrar frontend;
gerar abstrações artificiais;
transformar o sistema em “enterprise boilerplate”.
