Refatore completamente o módulo “Analytics” do sistema MUSIC OS 360 para transformá-lo em um módulo centralizado chamado “Relatórios”, com arquitetura limpa, reutilizável, escalável e sem duplicidade estrutural.

OBJETIVO:
O módulo atual “Analytics” está misturando:
- dashboards,
- métricas,
- importação,
- exportação,
- auditoria,
- integrações,
- relatórios operacionais.

A refatoração deve transformar esse módulo em uma CENTRAL DE RELATÓRIOS E OPERAÇÕES, removendo redundâncias existentes no sistema inteiro.

REGRAS OBRIGATÓRIAS:

1. RENOMEAÇÃO GLOBAL
- Renomear visualmente:
  Analytics -> Relatórios
- Atualizar:
  - rotas
  - breadcrumbs
  - labels
  - menus
  - permissões
  - navegação
  - titles
  - metadata
  - page headers

2. NÃO QUEBRAR O SISTEMA
- Preservar:
  - autenticação
  - permissões
  - layouts
  - providers
  - hooks globais
  - stores
  - APIs existentes
- Manter compatibilidade retroativa temporária quando necessário.

3. CENTRALIZAÇÃO DE IMPORTAÇÃO/EXPORTAÇÃO
Remover botões duplicados de:
- artistas
- contratos
- catálogo
- financeiro
- royalties
- lançamentos
- marketing
- qualquer outro módulo

Criar sistema centralizado de:
- Importação
- Exportação

Toda operação deve ser acessada via:
Relatórios -> Importar / Exportar

4. CRIAR NOVA ESTRUTURA

Estrutura ideal:

/modules/reports
  /pages
  /components
  /services
  /hooks
  /types
  /utils
  /templates
  /imports
  /exports
  /logs

5. SUBMÓDULOS

Criar páginas:
- Visão Geral
- Performance
- Financeiro
- Royalties
- Distribuição
- Contratos
- Catálogo
- Auditoria
- Importações
- Exportações
- Logs

6. TOOLBAR GLOBAL PADRONIZADA

Criar toolbar reutilizável contendo:
- filtros
- busca
- período
- importar
- exportar
- atualizar
- ações em lote

Os botões Importar e Exportar devem ficar alinhados à direita.

7. IMPORTAÇÃO

Criar engine reutilizável de importação:
- CSV
- XLSX
- JSON
- XML

Com:
- preview
- validação
- mapeamento
- tratamento de erro
- logs
- status
- rollback
- auditoria

8. EXPORTAÇÃO

Criar engine reutilizável de exportação:
- CSV
- XLSX
- PDF
- JSON

Com:
- filtros
- presets
- paginação
- seleção de colunas
- exportação parcial
- exportação total

9. AUDITORIA

Criar logs centralizados:
- quem importou
- quem exportou
- horário
- módulo
- quantidade de registros
- status
- falhas

10. REMOVER DUPLICIDADE

Eliminar:
- ImportButton duplicado
- ExportButton duplicado
- modais repetidos
- handlers redundantes
- hooks repetidos
- lógica espalhada

Consolidar tudo em componentes reutilizáveis.

11. PADRONIZAÇÃO VISUAL

Seguir padrão visual já existente:
- dark mode
- cards atuais
- spacing consistente
- tipografia consistente
- grid responsivo
- componentes reutilizáveis

12. ANALYTICS INTERNO

O nome interno “analytics” pode continuar apenas tecnicamente:
- services/analytics
- analytics engine
- analytics provider

Mas visualmente o sistema deve usar:
“Relatórios”

13. LIMPEZA TÉCNICA

Remover:
- arquivos mortos
- componentes não utilizados
- imports órfãos
- rotas antigas sem uso
- estados redundantes
- services duplicados

14. PERFORMANCE

Implementar:
- lazy loading
- code splitting
- memoização onde necessário
- paginação
- virtualização de tabelas se necessário

15. RESULTADO ESPERADO

O sistema final deve:
- parecer um ERP profissional
- possuir central operacional de relatórios
- ter importação/exportação centralizada
- eliminar poluição visual
- reduzir duplicidade estrutural
- melhorar manutenção futura
- melhorar escalabilidade

IMPORTANTE:
- NÃO gerar código fictício.
- NÃO criar placeholders desnecessários.
- NÃO duplicar componentes.
- NÃO criar novos padrões inconsistentes.
- Reutilizar o máximo possível da arquitetura existente.
- Fazer refatoração real e limpa.
